## Domain introduced

### ExecutionDispatch

One canonical dispatch exists per APS `SchedulePublication`.

It snapshots:
- dispatch code;
- publication identity;
- scenario;
- scheduling run;
- ProductionPlan;
- publication version;
- schedule fingerprint;
- operation count;
- lifecycle status;
- creator and lifecycle timestamps.

Lifecycle:
`DRAFT → RELEASED | CANCELLED`

`RELEASED` and `CANCELLED` are terminal in G5.1.

### ExecutionOperation

Each published APS scheduled operation becomes one MES operation identity within the dispatch.

The snapshot preserves:
- publication and published-operation identity;
- planning-operation identity;
- Plan;
- Taquilla;
- ProductLine;
- Article;
- RoutingRevision;
- RoutingOperation;
- planned Resource;
- Area / WorkCenter;
- deck position;
- product/routing sequence;
- operation code/description;
- requested quantity;
- planned start / planned finish;
- G5.1 status `PENDING`.

G5.1 deliberately does **not** persist:
- actual_start;
- actual_finish;
- produced quantity;
- scrap quantity;
- pause/setup timestamps;
- actual resource;
- operator execution identity.

Those remain deferred to G5.2/G5.3.

## Dispatch rules

- dispatch can only be created from a `CURRENT` G4 publication;
- one dispatch per publication;
- materialization is all-or-nothing;
- repeated materialization with the same publication and dispatch code is idempotent;
- a conflicting dispatch code for an already-dispatched publication is rejected;
- the publication must still be `CURRENT` when a DRAFT dispatch is released;
- if APS supersedes the source publication before release, release is blocked;
- once RELEASED, the dispatch is independent execution evidence and is not rewritten by later APS replans;
- G5 never mutates G4 publication state, G3 demand or G2 master data.
