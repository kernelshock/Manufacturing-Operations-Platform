## Model and lifecycle

New `ReworkCase` identity:
- source completed execution operation;
- explicit return execution operation in the same dispatch/ProductLine;
- case code and mandatory reason code;
- allocated Decimal-safe quantity;
- creator/time and return actor/time;
- lifecycle `OPEN → IN_PROGRESS → READY_TO_RETURN → RETURNED`.

New `ReworkStep` identity:
- ordered sequence within a case;
- G2 RoutingOperation reference restricted to the source routing revision;
- actual resource (active) and captured operation code/description;
- lifecycle `PENDING → RUNNING → COMPLETED`;
- explicit start/finish, actor and produced quantity.

Steps may revisit previously used RoutingOperations; that is how a physical repair loop is represented without changing the canonical routing graph.

## Governance

- case source must be COMPLETED and have explicit produced quantity;
- source and return target must be distinct operations from the same dispatch/ProductLine;
- return target must not already be COMPLETED;
- case creation replays idempotently by dispatch + case code, conflicting evidence is rejected;
- the case quantity is reserved from source output;
- sum of normal transferred WIP plus allocated rework across active cases may not exceed actual produced quantity;
- rework route can be edited only while case is OPEN;
- each step must reference an active routing operation in the source revision and an active resource;
- steps execute in declared order, with monotonic timestamps;
- each step output is explicit and cannot exceed its input quantity;
- return is explicit and requires all steps COMPLETED;
- return is blocked if final recovered quantity differs from case allocated quantity, or if target is no longer PENDING;
- repeat of identical START / COMPLETE / RETURN evidence is idempotent.

This initial scope does not automatically dispose of failed/scrapped rework output. Quantity loss stays unresolved until a governed disposition is introduced.

## Nominal WIP integration
