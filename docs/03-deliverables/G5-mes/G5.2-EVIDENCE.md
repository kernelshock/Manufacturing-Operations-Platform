## Execution lifecycle

`ExecutionOperation` now supports:

`PENDING → RUNNING → COMPLETED`

Rules:
- only operations belonging to a `RELEASED` dispatch can start;
- only `PENDING` operations can start;
- only `RUNNING` operations can complete;
- completion cannot precede actual start;
- completion requires an explicit positive Decimal-safe produced quantity;
- planned start/finish and requested quantity remain unchanged;
- produced quantity may differ from requested quantity;
- no scrap is inferred from the difference.

## Actual execution facts

G5.2 adds:
- `actual_start`;
- `actual_finish`;
- `produced_quantity`;
- `started_by`;
- `completed_by`.

Lifecycle constraints keep these fields consistent with operation status.

## Event evidence

New `ExecutionOperationEvent` records explicit execution actions:
- `START`;
- `COMPLETE`.

Each event retains:
- execution-operation identity;
- event type;
- event timestamp;
- produced quantity when COMPLETE;
- optional operator note;
- acting user;
- immutable creation timestamp.

The operation row is the consolidated current state; the event table is the explicit execution evidence.

## Idempotency and conflict behavior

- replaying the same START returns the existing event;
- replaying the same COMPLETE with the same quantity/timestamp/evidence returns the existing event;
- a repeated COMPLETE with a different produced quantity is a conflict;
- a repeated START/COMPLETE with conflicting explicit evidence is rejected;
- duplicate execution events are protected by database identity constraints.

## Quantity semantics

Produced quantity is an actual MES fact.

G5.2 deliberately does not require:
`produced_quantity == requested_quantity`.

The integration test validates:
- requested quantity = `10`;
- produced quantity = `9.5`;
- completion remains valid;
- no implicit scrap or demand mutation occurs.

This preserves truth: the difference is an observed execution variance whose classification belongs to later slices.
