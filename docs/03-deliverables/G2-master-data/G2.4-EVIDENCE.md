## Objective
Implement the canonical hierarchical BOM/ABM model defined in G0 without conflating routing stages with material demand.

The exact finished/intermediate `ArticleRevision` remains the parent identity. Product family/model similarity never substitutes for an exact manufacturing definition.

## Persistence
G2.4 adds:

- `md_bom_revision`;
- `md_bom_component`.

### BOMRevision
A BOM revision contains:
- exact parent ArticleRevision;
- revision number;
- effectivity interval;
- DRAFT / ACTIVE / SUPERSEDED / REJECTED status;
- source system;
- optional source batch;
- source fingerprint;
- creation timestamp.

Idempotency/uniqueness:
- parent ArticleRevision + revision number;
- parent ArticleRevision + source fingerprint.

### BOMComponent
A component relation contains:
- BOMRevision;
- child Article;
- optional pinned child ArticleRevision;
- Decimal(24,8) quantity;
- immutable raw source UoM text;
- optional approved canonical UoM;
- optional source/sequence relation metadata;
- optional Decimal scrap factor;
- optional line effectivity.

A source relation key is unique within one BOM revision when present.

## Revision safety
New BOM revisions start as `DRAFT`.

Only DRAFT revisions may receive component relations.

Publishing performs validation and changes the revision to `ACTIVE`; after publication, component mutation through the G2.4 API is rejected.

A controlled supersede operation:
- closes the previous ACTIVE revision with `valid_to`;
- marks it `SUPERSEDED`;
- activates the replacement at the same effective timestamp;
- requires both revisions to belong to the same parent Article;
- retains both historical definitions.

No published BOM is silently overwritten.

## Effectivity
BOM and component effectivity use half-open windows:

`valid_from <= t < valid_to`

where a null end means open-ended.

The service rejects invalid date ranges and overlapping ACTIVE BOM windows for the same exact parent ArticleRevision.

## Recursive explosion
The explosion engine:
1. starts from an ACTIVE/effective root BOM;
2. applies the requested root quantity using Decimal arithmetic;
3. multiplies each component quantity through every level;
4. applies an explicit scrap factor only when one is present;
5. resolves an effective child BOM where available;
6. records every traversed component before recursing;
7. preserves article/component path provenance;
8. aggregates only after path-level quantities are calculated.

The response contains:
- path-level lines for intermediate and leaf requirements;
- depth;
- leaf flag;
- Article IDs/codes in the complete path;
- component IDs in the complete path;
- UoM/raw-UoM;
- a post-path aggregate projection.

No binary floating-point arithmetic is used.

## Precision rule
G2.4 deliberately does not quantize intermediate explosion arithmetic merely to normalize JSON string scale.

Example:

`2 × 2 × 3 × 1.10 = 13.2`

may serialize with additional trailing zeros because PostgreSQL quantities and scrap factors have different Decimal scales. Numeric equality remains exact.

Rounding/conversion policy belongs to explicit UoM/reconciliation rules, not to the recursive multiplication engine.

## Child revision resolution
If a component pins `child_revision_id`, recursive resolution uses that exact revision.

If it does not pin a revision:
- the engine searches effective ACTIVE BOMs for that child Article;
- zero matches means the component is currently a leaf;
- one match is traversed;
- more than one match is rejected as ambiguous.

This prevents silent selection of an arbitrary manufacturing revision.

## Cycle detection
Cycles are checked before publication and again during explosion.

A direct self-reference is rejected at component creation.

Indirect cycles such as:

`A → B → A`

are rejected before the candidate BOM can become ACTIVE.

## Prolowin boundary
The G0 import contract remains enforced conceptually:

- a flattened complete Prolowin report can provide Article discovery, FIN projection and reconciliation evidence;
- it **cannot author parent→child BOM edges** because hierarchy/path information is absent.

G2.4 therefore provides the canonical hierarchical engine. Direct-structure ingestion and FIN reconciliation remain G2.7 responsibilities.
