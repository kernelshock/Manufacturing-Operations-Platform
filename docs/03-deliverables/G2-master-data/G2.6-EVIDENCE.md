## Objective
Represent nominal manufacturing availability and capacity without turning Master Data into an APS scheduling engine.

G2.6 defines when a governed manufacturing scope is nominally available. APS remains responsible for order sequencing, finite-capacity scheduling, planned start/finish timestamps and schedule transactions.

## Calendar identity and versioning
A ManufacturingCalendar contains:
- stable calendar code;
- display name;
- revision number;
- IANA timezone;
- exactly one target;
- day-granular valid-from / valid-to effectivity;
- DRAFT / ACTIVE / SUPERSEDED / REJECTED status;
- creation timestamp.

Target is exactly one of:
- G1 Plant;
- G1 Area;
- G1 WorkCenter;
- G1 Resource.

No duplicate organizational/resource master is introduced.

Within one calendar code:
- target cannot change between revisions;
- timezone cannot change between revisions;
- code + revision number is unique.

## Timezone semantics
Recurring working windows are expressed in the calendar's local civil time.

G2.6 validates IANA zone names through Python `zoneinfo`.

The reference FAIC timezone used in integration tests is:

`America/Argentina/Cordoba`

The released-runtime smoke was strengthened to resolve that timezone **inside the actual backend container image**, not only on the GitHub runner.

No additional timezone dependency was necessary for the current pinned runtime image.

## Weekly availability
A CalendarWeeklyWindow contains:
- weekday 0..6, Monday = 0;
- start minute;
- end minute;
- explicit spans-midnight flag;
- Decimal capacity factor;
- optional label;
- active state.

Same-day and overnight windows are supported.

Examples:
- 07:00–12:00 -> start 420 / end 720;
- 12:30–16:00 -> start 750 / end 960;
- 22:00–06:00 -> start 1320 / end 360 with spans_midnight=true.

Active recurring windows within one calendar may not overlap, including overlaps that cross the week boundary.

## FAIC schedule fixture
Automated integration evidence includes the established FAIC working-day semantics:
- Monday 07:00–12:00;
- lunch gap 12:00–12:30;
- Monday 12:30–16:00.

Resolution verifies:
- 10:00 -> available;
- 12:15 -> unavailable;
- 12:45 -> available.

The engine therefore exposes the lunch break as unavailable capacity rather than requiring APS to infer a pause.

## Dated exceptions
CalendarException kinds:
- `CLOSED`;
- `AVAILABLE_OVERRIDE`.

CLOSED may close:
- a full local date; or
- a same-day time interval.

AVAILABLE_OVERRIDE requires:
- an explicit same-day interval;
- positive Decimal capacity factor.

Examples covered by tests:
- planned resource maintenance closes 10:00–11:00;
- a Saturday recovery shift opens 08:00–12:00 at 0.5 capacity.

Exceptions on the same local date may not overlap.

## Resolution precedence
When availability is requested for a Resource, G2.6 derives its full G1 hierarchy:

`Resource → WorkCenter → Area → Plant`

The first effective published calendar is selected with deterministic precedence:

`Resource > WorkCenter > Area > Plant`

A Resource-specific calendar therefore fully overrides a Plant baseline for its effectivity interval.

Equivalent shorter fallback chains are used when the requested target is WorkCenter or Area.

## Rule precedence inside a calendar
For a selected calendar:
1. matching dated exception;
2. matching recurring weekly window;
3. otherwise unavailable.

Therefore:
- CLOSED overrides a normal working window;
- AVAILABLE_OVERRIDE can open a normally closed interval;
- no matching rule returns unavailable capacity.

The resolver returns:
- selected calendar/revision;
- selected target scope/id;
- timezone;
- requested timestamp;
- resolved local timestamp;
- available true/false;
- Decimal capacity factor;
- source rule;
- matching weekly-window or exception ID when applicable.

## Effectivity and historical truth
Calendar revisions use half-open day windows:

`valid_from <= local_date < valid_to`

A controlled supersede:
- requires current calendar ACTIVE;
- requires replacement DRAFT;
- requires same calendar code;
- requires same target;
- requires same timezone;
- closes the old revision on `effective_on`;
- marks old revision SUPERSEDED;
- activates replacement from the same local date.

Published revisions remain structurally immutable.

Critically, resolution considers both:
- ACTIVE;
- SUPERSEDED

published revisions, then chooses by their effectivity interval.

This means asking for a historical timestamp resolves the historical calendar revision instead of rewriting past production truth.

## APS boundary
G2.6 does **not** create:
- production orders;
- planned operation start/finish;
- dispatch sequence;
- finite-capacity allocation;
- Gantt tasks;
- schedule versions;
- actual execution timestamps.

Those remain APS/MES transactional responsibilities.

Master Data supplies only governed nominal availability and capacity factors.

## Rework
During implementation, supersede validation was hardened so the replacement revision can be validated while explicitly ignoring the one ACTIVE revision being retired at the same effectivity cut.

The first full validation after that hardening (#28) exposed a separate historical-resolution defect: the resolver searched only ACTIVE calendars, so an older timestamp could no longer resolve after its calendar became SUPERSEDED.

The resolver was corrected to use all published historical definitions (`ACTIVE` + `SUPERSEDED`) and then apply the effectivity window.

Run #30 validated the corrected domain behavior.

Run #32 additionally validated the IANA timezone inside the built runtime image and is the canonical final G2.6 validation.
