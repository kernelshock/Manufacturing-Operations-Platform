## Objective
Implement canonical versioned process/routing definition independently from BOM demand and bind executable operations to the organizational/resource truth already owned by G1 Core.

## Persistence
G2.5 adds:

- `md_routing_revision`;
- `md_routing_operation`;
- `md_resource_assignment`.

## Routing revision
A RoutingRevision contains:
- exact ArticleRevision;
- revision number;
- valid-from / valid-to effectivity;
- DRAFT / ACTIVE / SUPERSEDED / REJECTED status;
- source system;
- optional source batch;
- source fingerprint;
- creation timestamp.

Uniqueness is enforced by:
- ArticleRevision + revision number;
- ArticleRevision + source fingerprint.

New routing revisions start as `DRAFT`.

## Routing operation
Each operation stores:
- source operation code;
- canonical sequence number;
- preserved source description;
- optional G1 Area;
- optional G1 WorkCenter;
- operation kind;
- schedulable flag;
- completion-marker flag;
- optional Decimal nominal rate;
- optional rate UoM;
- active state.

Allowed operation kinds:
- `PHYSICAL_PRODUCTION`;
- `COSTING_ONLY`;
- `ADMINISTRATIVE`;
- `COMPLETION_MARKER`;
- `UNKNOWN`.

Sequence number is unique inside one RoutingRevision.

## Execution semantics
The transport/service boundary enforces:
- a completion marker must use `COMPLETION_MARKER`;
- a completion marker is never schedulable;
- only `PHYSICAL_PRODUCTION` operations can be schedulable;
- nominal_rate and rate_uom are supplied together;
- nominal rate is positive.

This makes APS eligibility explicit instead of inferring it from source operation codes.

## Core hierarchy reuse
G2.5 does not create parallel Area, WorkCenter or Resource masters.

References point directly to G1:
- `core_area`;
- `core_work_center`;
- `core_resource`.

When a WorkCenter is supplied without Area, the canonical Area is derived from the WorkCenter.

When both are supplied, hierarchy mismatch is rejected.

Resource assignments validate that the Resource belongs to the operation WorkCenter/Area when those constraints are present.

Inactive Area, WorkCenter or Resource records cannot be newly bound into the routing.

## Resource assignments
A ResourceAssignment stores:
- RoutingOperation;
- G1 Resource;
- principal flag;
- optional Decimal capacity factor;
- optional source batch.

One Resource can appear only once per operation.

At the service boundary, only one resource may be marked principal for an operation.

Completion markers cannot receive resource assignments.

## Publish validation
Only DRAFT routings may receive:
- operations;
- resource assignments.

Publish requires:
- at least one active operation;
- at most one completion marker;
- no overlapping ACTIVE RoutingRevision for the same exact ArticleRevision;
- active referenced resources;
- every schedulable operation to have a WorkCenter or ResourceAssignment.

Once ACTIVE, structure mutation through G2.5 endpoints is rejected.

## Supersede lifecycle
A controlled supersede operation:
- requires current routing = ACTIVE;
- requires replacement = DRAFT;
- requires both routings to represent revisions of the same Article;
- closes current `valid_to`;
- marks current `SUPERSEDED`;
- activates replacement at the same effective timestamp.

Historical routing truth remains addressable.

## Effective lookup
Consumers can request the RoutingRevision effective for:
- exact ArticleRevision;
- timestamp.

Zero matches returns not found.

More than one effective ACTIVE match is treated as a data-integrity ambiguity and rejected rather than selecting arbitrarily.

## Definition projection
A complete routing definition endpoint returns:
- RoutingRevision;
- operations in canonical sequence;
- ResourceAssignments for every operation.

This is the G2.5 baseline projection intended for later APS/MES consumption.

## BOM separation
Routing operations are not component-demand records.

The Prolowin contract remains:

`operation_code != FIN -> SourceOperationState / routing evidence`

Material requirements remain exclusively in BOM.

Therefore operation rows cannot be accidentally added to material demand.

## Process identity boundary
The G0 physical baseline reserved an optional `process_id`.

The current repository contains no canonical Process entity or governance contract.

G2.5 therefore does **not** invent an orphan Process master or accept arbitrary unvalidated Process UUIDs. Source operation code/description are preserved, while Area/WorkCenter/Resource use existing governed identities.

A future Process master can be introduced through an explicit architecture decision and migration without rewriting RoutingRevision identity.
