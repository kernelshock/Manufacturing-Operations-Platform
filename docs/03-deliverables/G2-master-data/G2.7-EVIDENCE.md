## Objective
Implement the G0 Prolowin manufacturing-definition boundary without allowing a flattened complete report to invent recursive BOM structure, double-count operation stages or overwrite historical canonical definitions.

## Source contracts
G2.7 supports two normalized transport boundaries.

### Complete article structure
`COMPLETE_ARTICLE_STRUCTURE`

Contract:
- schema version 1.0.0;
- source system PROLOWIN;
- source filename;
- source SHA-256;
- parser version;
- optional export timestamp;
- declared root article;
- source rows with article code, operation code, description, Decimal quantity and raw UoM.

This implements the accepted G0 FIN rule.

### Direct article structure
`DIRECT_ARTICLE_STRUCTURE`

Contract:
- schema version 1.0.0;
- source system PROLOWIN;
- source provenance;
- declared root article code;
- direct parent→child relations;
- optional source sequence/relation key;
- Decimal quantity;
- raw UoM.

This is the hierarchy-preserving input allowed to create candidate BOM edges.

## Immutable source staging
Complete-report rows and direct parent-child source relations are append-only.

PostgreSQL triggers reject:
- UPDATE;
- DELETE.

This is tested directly against PostgreSQL.

ImportBatch status remains mutable because it represents the processing state of the immutable evidence.

## Batch identity and idempotency
Import identity is:

`source_system + source_sha256 + parser_version`

An identical replay returns the existing ImportBatch instead of duplicating staged or canonical data.

Canonical Article identity remains:

`external_system + external_code`

Content-addressed ArticleRevision/BOMRevision fingerprints prevent identical manufacturing definitions from creating duplicate canonical revisions.

## FIN normalization
For `COMPLETE_ARTICLE_STRUCTURE`:
- every unique article code must have exactly one FIN row;
- the root must have exactly one FIN row;
- each FIN row becomes one flattened requirement;
- root FIN is marked `is_root=true`;
- root FIN is excluded from reconciliation component demand;
- every non-FIN row becomes SourceOperationState;
- non-FIN quantities are never summed into BOM/material demand.

Blocking conditions include:
- missing FIN;
- duplicate FIN;
- unresolved root.

A blocker changes the batch to REJECTED and prevents canonical application.

## Routing evidence
Non-FIN operation rows retain:
- article code;
- source operation code;
- source description;
- Decimal quantity;
- raw UoM;
- exact source row provenance.

Known corpus codes 010/020/025/030/040/050 are accepted as source evidence.

Unknown operation codes create `PLW_OPERATION_SEQUENCE_UNKNOWN` warnings.

G2.7 does not guess Area, WorkCenter or Resource from those codes.

## UoM governance
Raw Prolowin UoM text is preserved exactly in staging and normalized projections.

When no approved `UnitOfMeasureAlias` exists:
- an UNMAPPED alias is created;
- `PLW_UOM_UNMAPPED` WARNING is recorded;
- no canonical UoM is invented.

When an approved mapping exists, reconciliation may apply its explicit conversion factor.

## Article assimilation
Valid batches reuse one canonical Article per Prolowin business code.

Code prefix is never used to infer Article kind.

If kind remains UNKNOWN, `PLW_ARTICLE_KIND_UNKNOWN` remains visible as a warning.

Conflicting descriptions create DQ evidence instead of silently overwriting canonical description.

## Complete-report architecture boundary
The complete report can:
- discover/reuse Articles;
- preserve raw UoM;
- preserve operation evidence;
- create a flattened FIN snapshot;
- create content-addressed root revision evidence.

It cannot create:
- BOMComponent parent-child edges;
- recursive hierarchy;
- RoutingOperation WorkCenter/Resource mappings.

This implements ADR-0012 and the G0 import contract without inference.

## Direct hierarchy validation
Direct parent-child inputs are staged before canonical application.

Validation blocks:
- direct self-cycle;
- indirect recursive cycle;
- duplicate normalized relation;
- root with no outgoing relation;
- disconnected relation graph.

If any BLOCKER is open:
- batch = REJECTED;
- no candidate ArticleRevision/BOMRevision is created.

## Candidate BOM generation
A valid direct hierarchy creates or reuses:
- Article masters;
- content-addressed ArticleRevision records for parent articles;
- DRAFT BOMRevision candidates;
- BOMComponent relations.

Children that also have direct structures in the same graph are pinned to their exact ArticleRevision candidate.

No imported candidate is automatically ACTIVE.

Publication remains governed by the existing G2.4 lifecycle.

## Candidate recursive explosion
Reconciliation can recursively traverse DRAFT candidates without weakening the public G2.4 rule that the normal operational explosion endpoint accepts only ACTIVE BOMs.

The reconciliation-only traversal:
- starts at the selected exact BOMRevision;
- multiplies Decimal quantities through every level;
- follows pinned child ArticleRevision candidates;
- detects cycles;
- includes both intermediate and leaf Article requirements;
- aggregates after path calculation.

## Reconciliation
A reconciliation request contains:
- complete FIN batch;
- exact BOMRevision;
- Decimal absolute tolerance.

Before comparison:
- unresolved BLOCKER DQ on the complete/direct source blocks the run;
- complete snapshot root must equal BOM root;
- a mismatched root/BOM selection is a request error and **does not create source DQ**.

Comparison normalizes each side by:
- Article code;
- approved canonical UoM when available;
- explicit alias conversion factor;
- otherwise exact raw UoM.

Per-item results:
- MATCH;
- MISMATCH;
- SOURCE_ONLY;
- CALCULATED_ONLY.

Run results:
- MATCH;
- MATCH_WITH_WARNINGS;
- MISMATCH;
- BLOCKED.

Successful reconciliation marks applicable import batches RECONCILED while preserving all staged evidence.
