## Isolation model

What-if evaluation does not re-read live G2/G3 planning inputs.

The baseline run snapshots are cloned into an isolated candidate run:
- PlanningOperation;
- CapacityCandidate;
- ResourceAvailabilityInterval.

Exceptions are applied only to the candidate copy.

This prevents later master-data changes from silently altering a previously defined hypothesis and preserves an exact baseline/candidate comparison.

## Frontend

## Validation defect and correction

The first integration run exposed a persistence visibility issue.

The isolated CapacityCandidate and ResourceAvailabilityInterval clones had been added to the SQLAlchemy session but were not explicitly flushed before invoking the existing G4.4 solver. With the repository session configuration, the solver query did not see those pending capacity rows and correctly reported:
`schedulable operation has no capacity candidates`.

The correction adds an explicit `session.flush()` after building the isolated capacity snapshot and before solving.

No intermediate commit is introduced:
- candidate rows become query-visible to the solver;
- if evaluation fails, rollback still removes the entire candidate snapshot;
- the CURRENT publication remains unchanged.
