## Objective

Govern the lifecycle between calculated schedules and released planning evidence by separating:
- calculated SchedulingRun state;
- immutable published schedule snapshots;
- controlled replanning provenance;
- explicit supersession history.

A published schedule must never be rewritten in place.

## Atomic supersession

Initial validation exposed a lifecycle ordering defect.

The database correctly rejected insertion of publication v2 while v1 was still CURRENT because the partial unique index enforces one CURRENT publication per scenario.

The service was corrected to perform supersession atomically inside one transaction:
1. mark current publication SUPERSEDED;
2. flush that state;
3. insert replacement CURRENT publication;
4. copy immutable operation/segment snapshots;
5. commit.

If any later step fails, PostgreSQL rolls back the entire transaction and the previous publication remains CURRENT.

The invariant was not weakened or bypassed.

## Integration validation

The lifecycle test validates:
- publish v1 as CURRENT;
- create controlled replan from v1 with mandatory reason;
- produce a SCHEDULED replan candidate;
- compare candidate to published v1 before release;
- publish v2;
- v1 becomes SUPERSEDED;
- v2 becomes CURRENT and references v1 through `supersedes_publication_id`;
- v1 planned timestamps remain unchanged and independently readable;
- v2 can contain changed planned timestamps;
- publishing v2 again is idempotent;
- published v1 cannot be cancelled;
- publication history resolves to [(1, SUPERSEDED), (2, CURRENT)].
