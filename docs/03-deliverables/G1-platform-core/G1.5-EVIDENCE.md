## Implemented
A cross-cutting audit mechanism now records security and privileged business mutations in PostgreSQL.

Covered action families:
- authentication: login success, login failure and logout;
- IAM: user creation, role creation, permission grant and role assignment;
- Core: organization, plant, area, work-center and resource creation.

## Event model
Each audit event stores:
- immutable internal UUID;
- timezone-aware occurrence timestamp;
- actor user ID when known;
- actor username snapshot;
- stable action code;
- target object type and ID;
- scope type and ID when relevant;
- outcome;
- request correlation ID;
- source IP;
- structured JSON details.

Sensitive authentication material is intentionally excluded. Passwords, password hashes and raw opaque session tokens are not written to audit details.

## Database-level append-only enforcement
Migration `0004_g1_5` creates a PostgreSQL trigger:

`trg_audit_event_append_only`

The trigger rejects both UPDATE and DELETE operations on `audit_event`. Automated integration tests directly attempt both mutations and confirm PostgreSQL rejects them.

## Authorization
A new capability `audit.read` is seeded by migration and granted to the built-in ADMIN role. Audit access is read-only through:

`GET /api/v1/audit/events`

No HTTP endpoint exists to create, modify or delete audit records.

## Request correlation
Clients may provide `X-Request-ID`. When absent, MOP generates a correlation identifier for the audit event. This allows later operational tracing without exposing credentials.
